# تدقيق تغييرات المصادقة وحراس VIP

**التاريخ:** 2026-11-24
**خط الأساس:** `80ba567bbba36809af048259ce468c813366d379`
**النطاق:** قراءة فرق ملفات الواجهة والمصادقة والخادم المشترك في worktree `feature/kinglike-vip-merge`. هذا تقرير محلي فقط؛ لم تُشغّل اختبارات أو خوادم أو عمليات بناء، ولم تُنفّذ استعلامات قواعد بيانات.

## خلاصة

صُنّفت **23 مجموعة تغيير منطقية**؛ جُمعت مسارات API المتشابهة في مجموعة واحدة. منها تغييرات VIP مباشرة، وتغييرات حماية جلسات عامة، وتغييرات صريحة في سلوك خدمات أخرى. لذلك فالفرق الحالي **ليس minimal VIP diff**. لا توجد تعديلات مباشرة على منطق CRM أو WhatsApp أو Kay أو الدفع، لكن استبدال حارسي المصادقة المركزيين يؤثر في كل مسار يستخدمهما، بما في ذلك بعض مسارات هذه الخدمات والمدفوعات.

فرع `release/auth-priority` لا يضيف إلى الأساس تغييرات تطبيقية بحسب المقارنة المحلية؛ الفرق بينه وبين خط الأساس محصور بملفي ذاكرة. لا يثبت ذلك أن الدمج خالٍ من تعارضات نصية أو سلوكية، ولم يُجرَ دمج.

## تقييم الحد الأدنى المقترح

1. افصل حزمة **حماية الجلسة العامة** (المجموعات 1–8) عن حزمة VIP. هي تغييرات صحيحة الاتجاه أمنيًا، لكنها توسّع سطح التغيير إلى التطبيق كله؛ لا تُدمج بوصفها تبعية غير موضحة لميزة VIP.
2. أبقِ في فرق VIP: أعلام الواجهة والخادم الصارمة، تسجيل VIP بعد middleware الجلسة، حراسة كل API في الخادم، إخفاء بيانات VIP من سجلات الاستجابة، تنظيف cache عند تبدل الحساب، وتجاوز Service Worker لصفحات VIP.
3. أخرج تغييرات الخدمات غير المتعلقة بالميزة في المجموعات 9–15 من فرق VIP ما لم يعتمدها المالك كتحسين مستقل ويُختبر سلوكها. لا تُوسّع تعديل CRM/WhatsApp/Kay أو الدفع لمجرد وجود الحراس المركزية؛ اختبر أثرها غير المباشر إذا أُبقيت حزمة المصادقة العامة.
4. لا تغيّر code paths الخاصة بالدفع أو callback أو الإشعارات في هذا التقرير. فرّق بين فحص الجلسة وبين تنفيذ معاملة دفع أو إرسال إشعار.

## اختبارات regression المطلوبة لاحقًا

- **Login:** username/email/phone، ومسارات WhatsApp/Facebook التي تمر عبر تدفق التحقق الحالي؛ كلمات مرور صحيحة وخاطئة، توافق bcrypt والآلية القديمة المدعومة، حساب نشط/معطل/موثق/غير موثق، وقيمة null تاريخية إن أمكن إثبات وجودها في fixture. لا تستخدم حسابات حقيقية.
- **الجلسة:** cookie مجهول يتغير بعد دخول ناجح؛ لا يتغير بعد كلمة مرور خطأ أو حساب غير مؤهل؛ فشل `regenerate` لا يصدّر جلسة؛ تبديل مشتري إلى مشتري آخر يبطل cookie القديم؛ logout يبطل session ويزيل cookie مع خيارات cookie الصحيحة.
- **`/me` والحراس:** حساب محذوف/معطل/غير موثق، database unavailable، وسحب `isAdmin` أو تغيير role أثناء استمرار cookie؛ تحقق من `401/403/503` ومن مسح الجلسة عند الحاجة.
- **الأدوار:** buyer، seller، `sub_agent`، موظف CRM، admin، وغير admin يحمل role نصيًا مثل `admin` دون `isAdmin=true`. تأكد أن السلوك القديم المقصود محفوظ وأن role وحده لا يمنح امتياز المدير.
- **المسارات ذات الأثر خارج VIP:** حجوزات الاستشارات، الإشعارات، push، AI، العقارات الخاصة والمدونات. استخدم storage/PG اصطناعيًا، وتأكد من السلوك عند session سليمة، session قديمة، وإخفاق قراءة المستخدم.
- **Payments/BOG:** اختبارات stub-only لصلاحية session على create-order/status/refund؛ لا تستدعِ بوابة الدفع ولا تُنشئ طلبات خارجية ولا تُرسل أو تُحصّل أموالًا.
- **CRM/Kay/WhatsApp:** اختبار تكاملي stub-only للمسارات التي تستخدم `isAuthenticated`/`isAdmin`، مع تأكيد عدم تغيير ملكية lead أو حالة CRM أو بدء أي WhatsApp/Kay operation.
- **VIP:** العلم OFF يعطي `404` من الخادم ولا يسجل صفحات في العميل؛ ON لا يتجاوز الجلسة النشطة والموثقة؛ فصل بيانات المشتري؛ حدود تعيين البائع؛ admin revocation؛ تنزيل الإيصالات يخضع للدور؛ لا cache بين الحسابات؛ ولا migrations على startup.

## ما لم يُنفذ في هذه الجولة

لم تُشغّل الاختبارات أو البناء أو الخادم، ولم تُقرأ قيم بيئة أو أسرار، ولم تُجرَ اتصالات خارجية أو قواعد بيانات. لا توجد نتيجة عن قيم flags الفعلية أو nulls التاريخية في بيانات حية. التقرير وحده هو التغيير المقصود في worktree لهذه الجولة.

## ملحق تحقق لاحق داخل worktree المنفصل

- أُضيفت اختبارات HTTP محلية لمعالجات الجلسة الفعلية، وتسجيل الدخول باستخدام bcrypt، و`/api/auth/me`، وlogout، وتجديد الجلسة، وسحب صلاحية المدير، وفشل التخزين. كما أُضيف اختبار لمنع مستخدم من تعديل إشعار أو اشتراك Push يخص مستخدمًا آخر.
- عُزلت مسارات الإشعارات وPush في factories قابلة للاختبار. أصبحت تحديثات الإشعار والحذف والتحديث المتكرر لاشتراك Push مشروطة بهوية مالك السجل؛ محاولة استبدال مفاتيح اشتراك مستخدم آخر تفشل دون تغيير سجله.
- أُضيف فحص ثابت لمسار تنزيل إيصال VIP يؤكد أن المسار محمي، وأن الاستحقاق يُراجع لكل مالك/بائع أو مدير/موافق مالي، وأن الاستجابة `private, no-store` و`nosniff`. هذا فحص مصدر وليس اختبارًا لاتصال قاعدة البيانات.
- مجموعة الاختبارات الآمنة المنفذة: **79/79 ناجحة**. شملت HTTP محليًا على loopback ببيانات اصطناعية، واختبارات قواعد VIP وCRM/Kay؛ اختبارات قواعد البيانات، S3، ومزودي الدفع/الرسائل لم تُشغّل.
- بناء Vite للواجهة وesbuild للخادم نجح لكل من worktree الحالي والنسخة الأساسية `80ba567bbba36809af048259ce468c813366d379`. جرى البناء كملفات مؤقتة فقط؛ إعداد Vite لم يحمّل ملف إعداد المشروع أو `.env`، واستخدم `envDir` فارغًا وعلم واجهة VIP = `false`. حزمة الخادم لم تُنفذ.
- فحص TypeScript أعاد **116 تشخيصًا في الأساس و116 في الحالة الحالية**. تطابق 97 موضعًا؛ 19 موضعًا تحرك بسبب تغييرات الأسطر. بقي تشخيص `server/storage.ts` عن `status` موجودًا في النسختين عند الموضع نفسه؛ اختلاف النص المعروض سببه ترتيب اتحاد الأنواع فقط. لا توجد إضافة دلالية مؤكدة من دمج VIP.
- مسح أنماط الأسرار للملفات المبنية لم يعثر على تطابق. أُزيلت مخرجات البناء المؤقتة بعد الفحص. لم يُشغّل خادم أو migration أو اتصال بقاعدة بيانات أو خدمة خارجية، ولم تُقرأ أسرار.
