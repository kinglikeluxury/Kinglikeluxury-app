Implement Phase 1 of Developer Registration Center for Kinglike Luxury CRM.

MAIN GOAL:
Build an admin-only multi-developer registration system that prepares and manages registration of every new CRM lead into developer/company registration forms.

This protects Kinglike Luxury’s right to sell the client by registering the lead under our company before developer protection expires.

IMPORTANT:
This must be a multi-developer engine from day one.

Silk Development is only the first configured developer company.

Do NOT hardcode Silk-specific logic inside the engine.

All developer-specific settings must be stored in database configuration tables.

The engine must support unlimited future developer companies without code changes.

Adding a new developer later should require only admin configuration:
- company name
- form URL
- field mapping
- default values
- representative settings
- registration interval
- active/inactive status

No code deployment should be required when adding future developers.

VERY IMPORTANT SAFETY RULES:
Do NOT modify:
- authentication logic
- payment logic
- WhatsApp sending logic
- Meta lead webhook logic except adding a safe post-lead-created hook
- AI model settings unrelated to this feature
- public property pages
- property upload/edit pages
- existing CRM lead data destructively
- existing database tables destructively
- existing routes unrelated to this feature
- secrets or environment variables
- production deployment settings

Only add the Developer Registration Center feature and the minimum safe hooks needed for newly created CRM leads.

MULTI-DEVELOPER STRATEGY:
When a new CRM lead is created, the system must create registration records for ALL active developer_companies.

This means:
Even if the lead is interested in Silk, prepare registrations for all active developers configured in the system.

For Phase 1, only Silk is seeded.
But the architecture must support Petra, Gumbati, Next Partners, Ambassadori, Wyndham, Rotana, and future developers without code changes.

LEAD SOURCES:
Create developer_registration_records when a CRM lead is created from:
- Meta webhook
- Meta pull sync
- manual CRM entry
- Excel import if available

For Phase 1:
Do not submit externally automatically.
Set status = prepared or needs_review depending on required data availability.

RE-REGISTRATION RULE:
Every active submitted registration record should be re-registered every 40 days.

Set:
next_registration_at = last_registered_at + 40 days

If never submitted:
next_registration_at should remain null until submitted.

A scheduled job should run daily and mark due records as pending_re_registration when:
today >= next_registration_at
and lead status allows re-registration
and protection_status is not stopped or sold.

IMPORTANT:
In Phase 1, do not auto-submit re-registration.
Only show due records in the admin queue as Pending Re-registration with manual actions.

CRM LEAD STATUS RULES:

Continue registration and re-registration for these lead statuses:
- New
- No Answer 1
- No Answer 2
- No Answer 3
- Will Think
- Follow Up
- Hot Buyer
- Entering Lead
- Broker
- Deposited
- Reserved

Stop registration and re-registration for these lead statuses:
- Purchased
- Second Hand
- Junk Lead
- After 3 No Answer - Converted to Another Sales Manager
- Lost Competition
- Sold by Kinglike Luxury
- Not Interested
- Invalid Number
- Duplicate

If Sold by Kinglike Luxury or Not Interested do not currently exist in the CRM status list:
Do not break the CRM.
Add support safely only if the status list is centralized and easy to extend.
Otherwise only include them in stop logic for future compatibility.

When a CRM lead status changes to a stop status:
- mark related developer_registration_records as stopped
- set protection_status = sold if status is Purchased or Sold by Kinglike Luxury
- otherwise set protection_status = stopped
- cancel future re-registration
